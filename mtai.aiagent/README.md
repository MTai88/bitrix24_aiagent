# mtai.aiagent — AI-агент для Bitrix24 (открытые линии + чаты)

Модуль встраивает AI-агента в два канала портала:

- **Открытые линии** — автономные ответы клиентам по базе знаний (RAG):
  сообщение клиента → векторный поиск по загруженным документам → ответ LLM;
  если ответа нет или клиент просит человека — диалог передаётся оператору.
- **Личные чаты** — выполнение задач сотрудников в CRM и задачах:
  «Создай сделку для клиента Иванова на 100000 рублей», «Добавь задачу
  в сделку №123, позвонить завтра» — через function calling / JSON-протокол.

Бот регистрируется через **imbot.v2** в режиме **eventMode=fetch**:
модуль сам забирает очередь событий (`imbot.v2.Event.get`) — публичный
HTTP-эндпоинт для вебхуков не нужен. Обработка асинхронная: события
складываются в очередь заданий, которую двигают агенты Битрикса
(на стенде — сервис `bitrix-cron`, раз в минуту).

## Архитектура

```
Клиент / сотрудник ──► Битрикс24 (im) ──► очередь событий бота
                                                │  агент fetchEvents (раз в минуту)
                                                ▼
                                  imbot.v2.Event.get ──► mtai_aiagent_job
                                                                │  агент processQueue
                                                                ▼
                     ┌──────────────────────────────────────────┴───────────────┐
                     ▼                                                            ▼
             OpenLineHandler                                              ChatHandler
             (chat.entityType = LINES)                                    (chat.type = private)
                     │                                                            │
        RAG: VectorIndex (mtai_aiagent_chunk)                       LLM + инструменты (Tools/ToolExecutor)
        + история диалога (mtai_aiagent_conversation)                + история диалога
                     │                                                            │
                     ▼                                                            ▼
   imopenlines.bot.session.message.send                       imbot.v2.Chat.Message.send
   imopenlines.bot.session.operator / .transfer                crm.item.add/update/list
   imopenlines.crm.lead.create                                 tasks.task.add, user.search
```

Компоненты:

| Слой | Классы | Назначение |
|------|--------|------------|
| REST-доступ | `Rest\Client` | два режима авторизации: OAuth локального приложения или входящий вебхук + botToken |
| Бот | `Bot\Manager` | `imbot.v2.Bot.register/update/unregister/get`, eventMode=fetch, isSupportOpenline |
| События | `Event\Fetcher` | `imbot.v2.Event.get` (курсор `nextOffset` хранится в опции `event_offset`) |
| Очередь | `Queue\Processor` | атомарный claim по токену, 3 попытки, возврат «зависших» заданий |
| LLM | `Llm\*` | OpenAI-совместимый, YandexGPT, GigaChat (экспериментально), Mock; эмбеддинги провайдера или встроенный лексический |
| RAG | `Rag\*` | парсеры TXT/MD/CSV/HTML/DOCX/PDF, чанкер, векторный индекс на MySQL |
| Диалоги | `Conversation\Store` | последние N сообщений (контекстное окно LLM) |
| Журнал | `Logger` + `mtai_aiagent_log` | запросы к LLM, REST-вызовы, решения агента; страница в админке |

Таблицы модуля: `mtai_aiagent_document`, `mtai_aiagent_chunk`,
`mtai_aiagent_conversation`, `mtai_aiagent_job`, `mtai_aiagent_log`.

## Установка

1. Скопируйте каталог `mtai.aiagent` в `<портал>/local/modules/`.
2. Админка → «Настройки → Настройки продукта → Модули» → «AI-агент (открытые
   линии и чаты)» → **Установить**. Создаются таблицы, агенты и страницы админки.
3. Настройте связь с порталом (ниже) и зарегистрируйте бота.

Проверить состояние из консоли (в контейнере `php` стенда):

```bash
docker compose exec php php local/modules/mtai.aiagent/cli/worker.php options
docker compose exec php php local/modules/mtai.aiagent/cli/worker.php fetch
docker compose exec php php local/modules/mtai.aiagent/cli/worker.php process
docker compose exec php php local/modules/mtai.aiagent/cli/worker.php log tail 30
```

## Связь с порталом (REST-приложение)

Настройки: «Настройки → AI-агент → Настройки» (или `/bitrix/admin/settings.php?mid=mtai.aiagent`).

### Вариант A — локальное приложение (OAuth)

1. «Настройки → Интеграции → Добавить интеграцию», тип «Локальное приложение»:
   - название: AI-агент;
   - права: **Мессенджер (im), Чат-боты (imbot), Открытые линии (imopenlines),
     CRM, Задачи (task — именно так, без s на конце), Пользователи (user)**.
2. После сохранения скопируйте **Client ID** и **Client Secret** в настройки модуля.
3. Авторизуйте приложение: откройте в браузере (под администратором)
   ```
   https://<портал>/oauth/authorize/?client_id=<CLIENT_ID>&response_type=code&redirect_uri=https://<портал>/
   ```
   Разрешите доступ — в адресной строке появится `code=...`. Обменяйте его
   на токены:
   ```bash
   curl -d "grant_type=authorization_code&client_id=<CLIENT_ID>&client_secret=<SECRET>&code=<CODE>&redirect_uri=https://<портал>/" \
        https://<портал>/oauth/token/
   ```
   Полученный `refresh_token` вставьте в настройки модуля. Access-токены модуль
   обновляет сам (refresh-токен Битрикс ротирует — модуль всегда сохраняет свежий).

   **Внимание (box-версии):** на портале без интернета/лицензии эндпоинт
   `/oauth/authorize/` отвечает `verification_needed: License check failed`
   (проверка лицензии у контроллера Битрикса) — используйте вариант B.

### Вариант B — входящий вебхук + botToken (стенд)

1. «Настройки → Интеграции → Входящий вебхук» с теми же правами
   (im, imbot, imopenlines, crm, task, user — scope задач называется task).
2. В настройках модуля: «Режим авторизации» = «Входящий вебхук + botToken»,
   «Владелец вебхука» = ID пользователя, «Код вебхука» = хвост URL
   (`/rest/<USER_ID>/<КОД>/`).

Модуль вызывает REST напрямую по URL вебхука, а для методов бота
подставляет `botToken` (imbot.v2.*) и `CLIENT_ID` (imopenlines.*) —
именно так бот, созданный вебхуком, опознаётся порталом
(APP_ID вида `custom<токен>`). Регистрация бота при этом проходит
с `fields.botToken`, без приложения.

> На тестовом стенде bitrix24_test вебхук уже создан (см. `data.txt`),
> режим — webhook, портал доступен из контейнеров как `https://bitrix.local`
> (network-alias сервиса caddy в docker-compose).

## Регистрация бота

Кнопка **«Проверить бота тестовым сообщением»** на вкладке «Приложение и
бот» отправляет сообщение боту от владельца вебхука и тут же прогоняет
полный цикл (событие → очередь → ответ) — ответ появляется в чате
мгновенно, удобно для быстрой диагностики конвейера.

Кнопка **«Зарегистрировать»** на вкладке «Приложение и бот» либо:

```bash
docker compose exec php php local/modules/mtai.aiagent/cli/worker.php bot register
```

Бот создаётся с параметрами: `type=bot`, `eventMode=fetch`,
`isSupportOpenline=Y`, `isHidden=N`. Повторная регистрация того же кода
возвращает существующего бота. botId сохраняется в настройках.

### Подключение к открытой линии

«CRM → Открытые линии → (линия) → Очередь» — добавьте бота «AI-агент»
первым оператором (сортировка выше людей), чтобы сессии сначала попадали
боту. После передачи оператору (`imopenlines.bot.session.operator`)
бот в диалоге замолкает.

Опция «Линии (ID через запятую)» ограничивает линии, в которых агент отвечает
(пусто = все линии, где бот в очереди).

## Модуль 1. Открытые линии (RAG)

Обработка `ONIMBOTV2MESSAGEADD` для чатов `entityType = LINES`:

1. История сессии (до `history_depth` сообщений) + поиск по базе знаний
   (top-K фрагментов с косинусной близостью ≥ `rag_min_score`).
2. Системный промт (опция) + правила: отвечать только по контексту;
   если ответа нет — вернуть маркер `[ESCALATE]`.
3. Ответ клиенту: `imopenlines.bot.session.message.send`
   (CHAT_ID, MESSAGE, NAME=DEFAULT). Markdown-разметка ответа LLM
   автоматически конвертируется в BB-код мессенджера (`Chat\Markdown`):
   жирный, курсив, код, ссылки, списки.
4. Передача оператору, если:
   - клиент написал ключевые слова (оператор/менеджер/человек…);
   - релевантных фрагментов не нашлось (опция);
   - LLM вернула `[ESCALATE]` или упала с ошибкой;
   - **self-check** (опция «Контроль качества»): перед отправкой второй
     запрос LLM проверяет, что ответ подтверждается фрагментами базы —
     уверенная «выдумка» уходит оператору (вердикт ДА/НЕТ, при сбое
     проверки ответ отправляется — fail-open).
   Передача: сообщение `ol_handoff_text`, затем
   `imopenlines.bot.session.operator` (первый доступный) или
   `.transfer` на конкретного сотрудника (опция «Передавать сотруднику»).
5. Лид: на первое сообщение сессии один раз вызывается
   `imopenlines.crm.lead.create` (маркер «лид создан» хранится локально —
   REST не отдаёт текущие привязки линии к CRM).
6. Рабочие часы (опция «ЧЧ:ММ-ЧЧ:ММ» + дни): вне окна клиент получает
   сообщение «вне рабочих часов», диалог сразу уходит оператору.
7. CRM-контекст: сущности, привязанные к сессиям этой линии (лид/сделка/
   контакт/компания с названиями), подмешиваются в системный промпт —
   агент «видит», кто пишет и на какой стадии разговор.

## Модуль 2. Чаты (CRM-агент)

Обработка `ONIMBOTV2MESSAGEADD` в личных диалогах с ботом (`chat.type=private`):

- OpenAI-совместимые провайдеры — нативный **function calling**: цикл
  «tool call → результат → …» до финального ответа (≤6 итераций).
- YandexGPT/GigaChat — **JSON-протокол**: описание инструментов в системном
  промте, ответ строго `{"tool": "...", "arguments": {...}}` или
  `{"answer": "..."}`.

Инструменты — папка `lib/tools/<ИмяТула>/`: по папке на инструмент,
автоподхват без регистрации (см. «Добавление своего инструмента» ниже).

Инструменты (поставляются с модулем):

| Инструмент | REST-методы |
|------------|-------------|
| `crm_find_entities` | `crm.item.list` — по названию, стадии сделки (`stage_id`/`stage_semantic` open/won/lost), сумме (мин/макс), ответственному (имя→ID), дате создания (от/до), воронке (`category_id`/название, «Общая»=0), связанным компании/контакту (ID или название; контакт — по имени, фамилии и «Имя Фамилия»); критерии комбинируются (И) |
| `crm_create_entity` | `crm.item.add` (+ автопоиск/создание контакта) |
| `crm_update_entity` | `crm.item.update` |
| `crm_create_task` | `tasks.task.add` (+ `UF_CRM_TASK` привязка `L_/D_/C_/CO_`) |
| `tasks_list` | `tasks.task.list` — «мои задачи» (незавершённые/завершённые) |
| `task_complete` | `tasks.task.complete` — завершить по ID |
| `crm_add_comment` | `crm.timeline.comment.add` — запись в историю карточки CRM |
| `kb_search` | поиск по базе знаний: обе области по умолчанию, параметр `scope` = public/internal (внутренние регламенты сотрудникам) |
| `find_user` | `user.search`, `user.get` |

В системный промт автоматически подставляется контекст: текущие дата/время
и день недели (иначе модель не сможет вычислить «завтра»/«в пятницу» для
дедлайнов) и имя обратившегося сотрудника.

Ответ пользователю — `imbot.v2.Chat.Message.send`
(`botId`, `dialogId`, `fields.message` — ключ в lowerCamelCase, так
требует REST-шлюз контроллера). Действия от имени автора запроса (`ASSIGNED_BY_ID`/`CREATED_BY`), и —
главное — **с учётом его прав**: перед каждым действием AI-агент проверяет
нативные права CRM сотрудника (`Chat\AccessGuard`,
`Container::getUserPermissions($userId)`, без авторизации):
- `crm_find_entities` показывает только сущности, доступные на чтение
  (права «свои/отдел/все» из ролей CRM);
- `crm_create_entity` — только при праве добавления;
- `crm_update_entity` и `crm_add_comment` — только при праве изменения;
- `crm_create_task` с привязкой — только при праве чтения сущности
  (привязка выдаёт факт её существования);
- `task_complete` — только участнику задачи (создатель/исполнитель/
  соисполнитель/наблюдатель).
Отказ возвращается модели как ошибка — она сообщает сотруднику
человеческим языком; факт отказа пишется в журнал (категория `access`).
REST при этом ходит от владельца вебхука — но без guard-проверки действие
не выполняется. То же действует в активности БП (параметр «ID пользователя»).
Список разрешённых пользователей — опция (пусто = все сотрудники).

### Добавление своего инструмента

Новый инструмент = новая папка в `lib/tools/` — и он сразу доступен агенту
(чат + активность БП), ничего регистрировать не нужно:

```
lib/tools/GetWeather/            ← PascalCase, любое имя
├── config.php                   ← описание для LLM (JSON Schema)
└── Tool.php                     ← класс с execute()
```

`config.php` возвращает массив:

```php
<?php
return [
    'name' => 'get_weather',     // имя тулса для LLM (snake_case)
    'description' => 'Текущая погода в городе. Используй для вопросов о погоде.',
    'parameters' => [            // JSON Schema параметров
        'type' => 'object',
        'properties' => [
            'city' => ['type' => 'string', 'description' => 'город'],
        ],
        'required' => ['city'],
    ],
];
```

`Tool.php` — класс `Tool` с методом `execute(array $arguments, int $userId, Context $ctx): array`.
Возвращайте данные для модели либо `['error' => 'причина']` — модель сама
объяснит сотруднику. В `$ctx` — REST-клиент портала (`$ctx->restCall()`,
`$ctx->restSafe()`) и константы CRM; права проверяйте через
`AccessGuard::crmCanRead/Update/Add`. Результат пишите в журнал
`Logger::info('tools', ...)` при необходимости.

```php
<?php
namespace Mtai\Aiagent\Tools\GetWeather;

use Mtai\Aiagent\Tools\Context;

class Tool
{
    public function execute(array $args, int $userId, Context $ctx): array
    {
        $city = trim((string)($args['city'] ?? ''));
        if ($city === '')
        {
            return ['error' => 'укажите город'];
        }

        // ... любой код: внешние API, REST портала, БД ...

        return ['city' => $city, 'temperature' => '+17', 'condition' => 'ясно'];
    }
}
```

Правила: имя папки = последний компонент namespace; `name` в config —
уникальное snake_case; папка без `config.php` или `Tool.php` молча
пропускается (ошибка — в журнал, категория tools).

### Слэш-команды бота

Регистрируются вместе с ботом (`imbot.v2.Command.register`, события
`ONIMBOTV2COMMANDADD` попадают в ту же очередь):

| Команда | Действие |
|---------|----------|
| `/ai-help` | справка: что агент умеет |
| `/ai-add` | добавить в базу знаний файл, приложенный к сообщению с командой |
| `/ai-reset` | сбросить память текущего диалога |
| `/ai-status` | состояние: бот, база знаний, очередь, последний опрос событий |

Ответ идёт через `imbot.v2.Command.answer` (id команд сохраняются в
опции `bot_command_ids`). Команды работают и в чатах открытых линий.

`/ai-add` — пополнение базы знаний прямо из мессенджера: приложите
документ (PDF/DOCX/TXT/MD/CSV) к сообщению, напишите `/ai-add` и отправьте —
бот разберёт файл (нативно, через `Im\V2\Message->getFiles()` + Disk),
проиндексирует и ответит, сколько фрагментов получилось.

### Уведомления о сбоях

Задание очереди, упавшее 3 раза, помечается ошибкой, и бот пишет
администратору (опция «Уведомлять пользователя») в личный чат
короткий отчёт с причиной.

## Активность для бизнес-процессов «AI-агент»

В дизайнере бизнес-процессов (списки, смарт-процессы, документы) доступна
активность **«AI-агент»** (группа «ИИ») — аналог узла AI Agent в n8n:
на входе вопрос/задача и настройки, на выходе — ответ модели в поле
«Ответ агента». Модель, ключ и эмбеддинги берутся из настроек модуля —
провайдера достаточно настроить один раз.

Поля активности:

| Поле | Назначение |
|------|-----------|
| Вопрос / задача | текст с вставками полей документа (`{=Document:NAME}` и т.п.) |
| Режим | «Ответ ассистента» — RAG-ответ по базе знаний; «Выполнить задачу» — инструменты CRM (те же, что у чат-агента); «Прямой запрос к модели» — вопрос к LLM без базы знаний и инструментов (генерация текста, суммаризация, классификация и т.п.) |
| Системный промпт | переопределяет роль из настроек модуля |
| Ключ памяти | например `{=Document:ID}` — контекст сохраняется между запусками активности с тем же ключом (несколько шагов одного диалога); пусто = одноразовый запрос |
| ID пользователя | от чьего имени выполняются CRM-действия в режиме «Выполнить задачу» |
| Поле документа для ответа | например `NAME` или `PROPERTY_123` — ответ сразу записывается в документ (пусто = не записывать) |
| Модель | переопределение LLM-модели для этого узла (пусто = из настроек модуля). Примеры: `gpt-4o-mini`, `yandexgpt-lite/latest`, `GigaChat-Lite` |

Результаты (доступны в последующих действиях и «Изменить переменные»):
**Ответ агента** (Answer), **Ошибка выполнения** (ErrorMessage).

Технически: класс `CBPMtaiAgentActivity` (BaseActivity, авто-диалог из
`getPropertiesMap`) устанавливается в `/bitrix/activities/custom/mtaiagentactivity/`
(bizproc сканирует этот каталог); оркестрация — `Agent\Runner`
(RAG-режим) и общий с чатом `Agent\ToolLoop` (function calling/JSON-протокол).
Активность появляется в палитре в собственной группе **«AI-агент»**
(`CATEGORY: ID=other, OWN_ID=mtai`) — работает и в классическом дизайнере
(iblock/lists), и в редакторах роботов. Если после правки описания активность
пропала из палитры — сбросьте кеш реестра: `ManagedCache->cleanAll()`.

## LLM-провайдеры

| Провайдер | Ключ | Особенности |
|-----------|------|-------------|
| OpenAI / OpenAI-совместимый | API-ключ | OpenAI, OpenRouter, vLLM/Ollama/LiteLLM — меняйте «Базовый URL»; нативный function calling |
| YandexGPT | API-ключ + folder id | эмбеддинги `text-search/latest`; инструменты через JSON-протокол |
| GigaChat | authorization key + scope | Base64(client_id:client_secret) из кабинета; access-токен (~30 мин) модуль получает и обновляет сам; **scope** задаётся в настройках (по умолчанию `GIGACHAT_API_PERS`, поддерживается B2B/CORP — должен соответствовать ключу); при ошибках SSL отключите проверку сертификата |
| Мок | — | эхо-ответы без внешних вызовов; для проверки конвейера |

Эмбеддинги базы знаний (опция «Режим»):

- **auto** — эмбеддинги LLM-провайдера, если поддерживает, иначе встроенный;
- **provider** — только провайдер;
- **hash** — встроенный лексический (хэш-трюк по словам и 6-символьным
  «стемам», без внешних API; качество ниже нейросетевых — не понимает
  морфологию дальше префикса, «поддержка» ≠ «техподдержки»);
- **off** — поиск отключён (агент линий всегда передаёт диалог оператору).

Секреты хранятся в БД зашифрованными (AES-256-CTR через
`Bitrix\Main\Security\Cipher`, ключ `crypto_key` из `bitrix/.settings.php`).
Переменные окружения приоритетнее БД: `MTAI_AIAGENT_LLM_API_KEY`,
`MTAI_AIAGENT_WEBHOOK_PASSWORD`, `MTAI_AIAGENT_APP_CLIENT_SECRET`,
`MTAI_AIAGENT_APP_REFRESH_TOKEN`.

## База знаний (RAG)

У базы знаний две области:

- **Публичная** (`public`) — по ней отвечает AI-агент открытых линий
  клиентам; сюда — FAQ, прайсы, условия доставки/возврата;
- **Внутренняя** (`internal`) — только для сотрудников: регламенты,
  внутренние прайсы, инструкции. Доступна чат-агенту (инструмент
  `kb_search`, по умолчанию ищет по обеим областям) и активности БП
  «Ответ ассистента»; клиентская линия её **никогда не отдаёт** —
  поиск линий ограничен областью `public` на уровне VectorIndex.

Область выбирается при загрузке документа (и видна колонкой в списке,
фильтр `?scope=internal`). Перевод документа в другую область —
переключите поле и загрузите файл заново (или через CLI).

Страница: «Настройки → AI-агент → База знаний». На ней же — «Проверка
поиска»: введите запрос и увидите топ-10 фрагментов со скорами — удобно
подбирать порог релевантности. Страница журнала показывает сводку за сутки
(события по категориям, очередь, размер базы знаний). Форматы:

- **TXT / MD / CSV / HTML** — рекомендуется для FAQ: разделение вопросов
  пустой строкой даёт по чанку на вопрос-ответ.
- **DOCX** — текст из `word/document.xml` (абзацы сохраняются).
- **PDF** — минималистичный парсер без внешних библиотек: текст из потоков
  (FlateDecode) по операторам Tj/TJ. **Не поддерживает** сканы (нет текстового
  слоя) и экзотические кодировки шрифтов — для таких документов
  пересохраните в DOCX/TXT.

Рекомендации по подготовке документов:

- один документ = одна тема (прайс, инструкции, FAQ);
- структурируйте парами «Вопрос: … Ответ: …» или заголовок + абзац —
  чанкер режет по пустым строкам и НЕ склеивает соседние блоки;
- конкретика вместо общих фраз: цифры, сроки, условия попадают в ответ
  только если есть в тексте;
- избегайте таблиц шире пары колонок — при простом извлечении текста
  теряется структура.

Чанкование: блок между пустыми строками = чанк; блок длиннее
`rag_chunk_size` (по умолчанию 1000 символов) режется по предложениям
с перекрытием `rag_chunk_overlap` (180). После смены модели эмбеддингов
или параметров чанкования нажмите «Переиндексировать всё».

Порог релевантности `rag_min_score` (косинусная близость, 0..1):
встроенный лексический эмбеддер — 0.15–0.25, нейросетевые эмбеддинги —
0.3–0.45. Ниже порога фрагменты не попадают в контекст; пустой контекст
(при включённой опции) передаёт диалог оператору.

Объём: индекс рассчитан на десятки тысяч фрагментов (перебор с косинусом
в PHP). Для больших баз подключайте внешний движок (Qdrant/OpenSearch kNN)
в `Rag\VectorIndex`.

## CLI-воркер

```
worker.php fetch|process|loop        — тик/цикл фетчера и очереди
worker.php bot register|update|unregister|status
worker.php kb list|reindex <id>|reindex-all|delete <id>
worker.php jobs                      — последние задания очереди
worker.php log tail <n>              — журнал
worker.php rest METHOD '{json}'      — произвольный REST-вызов (от имени модуля)
worker.php options                   — сводка состояния
```

## Проверка конвейера без LLM-ключей

1. Провайдер = «Мок», эмбеддинги = «auto» (встроенный лексический).
2. Загрузите FAQ на странице базы знаний.
3. Напишите боту в личный чат: ответ придёт с префиксом `[mock]`
   (эхо запроса) — конвейер «событие → очередь → LLM → ответ» работает.
4. `worker.php log tail` покажет шаги: REST-вызовы, rag search, очередь.

Для реальных ответов переключите провайдера на OpenAI-совместимый/YandexGPT
и задайте ключ. Открытые линии проверяйте через виджет (см. ниже).

## Проверка открытых линий на стенде

REST-создание клиентского диалога виджета в ядре отключено
(`imopenlines.widget.chat.create` помечен beta), поэтому полный e2e
линий проверяется вручную:

1. Бот добавлен в очередь линии (первым оператором).
2. «CRM → Открытые линии → Виджет на сайте» — откройте страницу с виджетом
   (или тестовую страницу линии) в браузере инкогнито и напишите в чат.
3. Ответ бота появится в течение минуты (тик агентов); в журнале —
   `rag search`, `llm answered`, `bot.session.message.send`.
4. Напишите «позовите оператора» — бот попрощается и передаст диалог.

## Удаление

Кнопка «Удалить» на странице настроек сносит бота (imbot.v2.Bot.unregister).
Удаление модуля в «Настройки продуктов → Модули» убирает таблицы, агентов и
страницы; REST-приложение/вебхук и загруженные в CFile документы удаляйте
вручную (вебхук модуля на стенде — см. `data.txt`).
